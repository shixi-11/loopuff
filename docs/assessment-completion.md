# Completed output versus a waiting task

All thirteen independent lessons currently accept their correct example followed by an unresolved receive as a 100-point success. Their finish action trusts that grade. Dispatch and diagnostics separately reject waiting, while the ordinary guide correctly exposes it as an observable language state. Waiting is valid Tolang quiescence; it is not completion of these finite tasks.

Make the shared finite-task assessment require no outstanding waiting receives before accepting a task. Preserve real output and method evidence, withhold the 20 execution points while the task is waiting, and return the existing waiting reason. Output and concept points remain earned for the work actually observed. The task cannot pass with a perfect score while its execution is unfinished. Completed, failed-output, failed-concept and runtime-error programs retain their existing rules.

Keep run/compile semantics, guide observations, route layout, translations, the thirteen goals, stored drafts/attempts/best scores/completions and save formats unchanged. Reading a corrected report must not rewrite historical records. Remove the redundant post-grade waiting overrides in dispatch, diagnostics and whole-program rewrite, since they should consume the shared decision rather than disagree about scores or completion. All three vault mechanisms have the same false-pass issue and use the same finite-task entry, without changing their valid signals or rewards. No new scoring field or mastery claim.

Compatibility: the established generic assess/grade interface is also used to observe language output and concept contribution, including valid waiting states. A full-suite counterexample explicitly requires that observation to remain conceptMissing/70 when an unused waiting join did not contribute to the output. Keep that interface unchanged; assessTask/gradeTask are the explicit finite-task entry points for app, rewrite, dispatch, diagnostic and vault. Both use one implementation with a completion policy, and the same error conversion. This preserves the language-observation contract without weakening any user-facing task's completion check or altering existing tests.

Verification: reproduce the false pass for every lesson; assert real waiting and expected outputs first, then failure/no perfect score and retained output/concept evidence. Check outstanding and resolved joined receives, valid waiting observations outside assessment, the shared callers, distinct correct solutions, runtime errors and pure old-save report reads. Run required frontend checks/build, independent review, Git sync and live assets/affected entries. Browser control is disabled in Work settings, so actual result-page rendering and continue-button interaction require later verification; source/runtime checks cannot stand in for that UI evidence.
