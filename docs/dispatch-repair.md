# Repairing a dispatch program

The existing Arcade dispatch missions already start with broken branch, manifest and function programs, followed by an independent relay task. This change makes their repair loop honest and actionable: a batch must finish, every required output must carry its own method evidence, and the selected batch offers a way to inspect the specific value that failed.

Two reproducible counterexamples were accepted before this change. All four missions could display every expected log while leaving a receive waiting (the function case returns a reply before starting that receive). The seed-0 manifest could hard-code the outputs for dock 4 as `5` and borrow the addition evidence from the neighbouring dock 2 output. The regression tests must fail on the original source and reject both patterns after the fix. Distinct correct programs and an empty manifest must still succeed.

The existing assessment option `eachOutputRequire` is reused; no new interpreter rule or notion of correctness is introduced. Waiting is rejected at the dispatch adapter, as already done by diagnostics and whole-program rewrites. Current results are recomputed from saved submitted source. Old drafts, stamps, rounds and historical clear records are preserved; the change only controls the current report and new awards.

Feedback is derived from the selected batch's actual report: execution error, pending receive, equal-threshold boundary, empty manifest, first differing output, or the first output missing a required method. A trace action opens and focuses the actual output/source/name snapshot when that output exists. It cannot show a fabricated step for a missing output or supply a replacement program. Selecting a different batch must change the feedback without changing source, submission, progress or awards.

Scope excludes save-format changes, new missions or navigation, timer/game mechanics, art, global typography and a full Tolang/compiler claim. The public copy is localized in all 11 languages. Checks cover failing-before/passing-after counterexamples, alternative correct solutions, feedback selection, trace focus, narrow/RTL layouts, old save retention and the live deployment.

Validation: 232 frontend checks and the static build passed. A read-only reviewer directly compared the five counterexamples against 6da58e9 (all previously accepted, all now rejected), checked 12 reasonable alternative solutions across three seeds and preserved empty manifests. Actual browser testing verified mixed constant output feedback, exact trace focus, selected batches, equality, pending receive rejection, a repaired 10/10 branch, reload retention and 11 locales at 390×640 without horizontal overflow. Arabic text stayed RTL and code stayed LTR; all temporary metrics were cleared. No native interpreter, backend or persistent format changed.
