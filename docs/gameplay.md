# Code-driven exploration

The learner reads a short program, predicts its output, changes it and checks an observable result. Existing signal, addition and name missions remain; the fourth mission transfers those ideas to an aircraft jumping between islands.

## Jump mission contract

This game interprets exactly one displayed integer in 0–12 as a forward distance. This is an application convention, not a new Tolang instruction. The introductory runner evaluates the program normally. The scene consumes the resulting log; it does not fabricate output or compare source text to an answer.

The demonstration targets five spaces, the modification targets seven and the independent task targets six using addition. Short and long jumps have different observable positions and feedback. A literal six may land but does not meet the independent addition requirement. Distinct correct programs receive the same task credit.

The learner may run without submitting, edit after a failed jump, and submit separately for the existing assessment. Editing clears both the scene's old outcome and any stale grade. UI navigation, translation and reload continue to preserve course progress and drafts.

One scene owns one animation loop and a resize observer. Navigation disposes both. Reduced-motion mode shows the same final position without travel animation. The visual scene is transient and is never a saved mastery flag.

## Verification

Runner-to-movement tests cover distinct solutions, short and long jumps, unsupported or ambiguous output, zero distance and exact animation endpoints. Existing course, scoring, routing and translation tests remain required. Browser checks must cover the full fourth-mission flow, trial before grading, correction after a miss, replay, edited-grade invalidation, language switching, narrow layout and reduced motion. These checks do not prove beginner learning effectiveness or completion of the full curriculum.

## Vault Run

A localized `/play/` page links to the vault at `/play/vault/` and the existing jump lesson. The home artwork, centered title, green accent, aircraft, four lessons and independent assessments remain intact. The course and arcade navigation labels are distinct.

The fictional star-bank mission has three mechanisms: output a sum, try a binding in an energy calculation, then independently send three increasing values in the required order. The same original interpreter runs the code. A CSS perspective door and sequential receivers visualize the output; no real bank systems or lock interfaces are involved. This is a programming puzzle with a dimensional illustration, not a free-roaming WebGL level.

A fixed per-run seed gives reproducible clues. Every submitted program is executed; different solutions that produce the required ordered output are accepted. Variable use is encouraged and explained, but printing the correct values also opens the mechanism. The game therefore demonstrates output and sequence without claiming that success proves understanding of variables. Stronger independent transfer assessments belong to the curriculum.

The first two mechanisms provide editable starting code. The third starts empty. Hints are optional and explain each operator as well as an executable example. Wrong values and wrong order produce actual receiver feedback. Unsupported syntax is localized. Editing cancels pending animation and invalidates the prior outcome; replaying with new clues clears this run but retains the three distinct mechanism stamps. Stamps are browser-local challenge history, cannot accumulate beyond three, and are not leaderboard scores or mastery certificates.

Drafts, clue seed, stage, submitted source and stamps persist across reload and language changes. Deleted drafts remain empty. The first pass is untimed; motion can be reduced. One mounted controller owns its timers and removes listeners on navigation. No account or cloud state is implied.

## Exploration records and lesson recovery

The lesson selector and playground share a browser-local flight log: completed
course missions, distinct vault mechanism stamps and exploration points. Each
unique completed course mission contributes 100 points and each unique stamp 50;
the current content therefore has a 550-point ceiling. Repeating a mission or
changing vault clues cannot farm additional points. Existing completions count
when this version first opens. Flight typing points and assessment grades are
separate and do not contribute to this total.

Each course mission now owns its own draft, learning step and submitted source.
Navigation, reload and language changes restore that mission's work. An explicit
replay restarts only the selected mission; completed-mission rewards remain.
The previous single-mission save migrates in place. Changing a submitted program
invalidates its assessment, including after restoring the mission. Playground
cards show saved progress, and the next-mission link targets the first unfinished
course mission, then the vault when its stamps are incomplete.

These records remain local to this browser. They are not accounts, a cloud save,
a verified leaderboard or a measurement of programming mastery. Account-backed
features require a separately configured service and remain queued.

## Queued game directions

These remain concepts, not playable releases:

- A larger bank infiltration: read patrol states, choose a route, operate interdependent devices and reach a vault. Teach sequencing first, then conditions and loops only after their supported language semantics are verified.
- A rising-water escape: predict water changes, control pumps and doors, then earn an optional timed challenge after untimed practice. Pause and retry remain available for learning.
- Code-triggered flight abilities and traversal: power, distance and resource costs have visible consequences.
- Pet care and battles: observe attributes, choose actions, trace how programs change a persistent companion. Preserve the approved aircraft as the home explorer.
- Account-backed progress, earned cosmetics, points and server-verified rankings. Browser-local stamps are not a substitute for these systems.

Every mode should require observation, a player decision, an executed program and visible consequences, with later tasks removing scaffolding. New visuals must serve that loop. Full language mastery, beginner learning outcomes and large-scale content coverage remain unverified.
